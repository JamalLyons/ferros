Ferros

A debugger for Rust, written in Rust, from the syscall up. No LLDB, no GDB, no debugserver underneath. On Apple Silicon, Ferros handles Mach exceptions itself, reads Mach-O and DWARF line tables, unwinds the stack, and sets breakpoints and steps from a CLI. Early development · macOS Apple Silicon today · Linux and Windows planned

No LLDB underneath

Every layer above the kernel is Rust you can read. DWARF line tables and unwind sections are consumed with gimli and addr2line. Mach-O is read with the object crate inside ferros-macos. Names are demangled with rustc-demangle.

Mach exception ports

The macOS backend takes the task's exception ports and reports breakpoints, signals, and exits to the session. Verified by tests/exceptions.rs.

Mach-O and dyld

Mach-O, universal binaries, and dSYM bundles, plus dyld's image list and the symbol tables of mapped shared-cache libraries.

DWARF and unwinding

Line tables, demangled names, compact unwind, and DWARF CFI, including inlined frames and signal frames.

Session and REPL

Software breakpoints, hardware single-step, and source step over, into, and out, driven from a line-oriented CLI. The engine forbids unsafe code.

What the others are built on

LLDB and GDB

C and C++ debuggers, mature after decades. Rust values arrive through pretty-printers on that model.

CodeLLDB

A Rust extension that drives LLDB, so the runtime under it is still LLDB.

debugserver

The helper LLDB uses on macOS. Ferros talks to Mach exception ports on its own.

What Ferros Brings

Rust above the kernel

Mach exception ports, Mach-O, dyld's image list, DWARF line tables, and unwinding live in this repo.

One portable engine

ferros-core forbids unsafe and has no OS dependency. CI checks that boundary. macOS stays in ferros-macos.

Early, on Apple Silicon

macOS arm64 is the verified target. Value inspection is the next phase. Linux and Windows are each planned as their own backend crate.

Works today

Each of these is exercised by an integration test on macOS arm64. Locals, print, async tasks, MIR, borrow visualization, and zero-cost breakpoints are on the roadmap below.

Mach exception handling

Launch suspended or attach by PID. Stops for breakpoints, signals, and exits come from a Mach exception-port loop.

Breakpoints and stepping

Software breakpoints by address, file:line, or function. Source step over, into, and out, plus one instruction, with other threads held.

DWARF line tables and unwinding

Demangled names, line tables, compact unwind, and DWARF CFI. Backtraces include inlined frames.

CLI and REPL

ferros launch and ferros attach, interactive, piped, or batch. Backtrace, registers, memory, threads, and images.

Architecture

The running debugger is the CLI, a portable engine, and the macOS backend. ferros-core forbids unsafe and has no OS dependency. ferros-mir is empty, ferros-ui is parked, and ferros-protocol is reserved for a future agent and editor protocol. The REPL accepts --batch and a pipe today. Architecture guide · ADR 0001

A debugger you can read, from the syscall up.

Ferros is a from-scratch debugger for macOS arm64. The engine stops, breaks, steps, and prints a symbolicated backtrace, and the platform stays in one crate. The longer aim is a Rust-native view of values, ownership, and MIR. That starts with value inspection, which is the next phase. The REPL takes a batch file or a pipe today. A protocol that hands stops to agents and editors is planned.

Build it on an Apple Silicon Mac.

Ferros is in early development and is not on crates.io. Clone the repo and build from source. Debugging another process needs an ad-hoc signature with the debugger entitlement in crates/ferros-macos/ferros.entitlements.
